Project onboarding · 10–15 minutes

From Swagger spec to reviewed, automated API tests

Follow one safe, read-only Petstore example to see how the agent derives test candidates, lets you review them, and runs only the plan you explicitly approve.

TypeScript Playwright API testing OpenAPI / Swagger Guided approvals

Before you begin

Open a terminal in the project root. You need Node.js 20+ and installed project dependencies. This walkthrough downloads Petstore's live Swagger 2.0 spec, so the generated route and authentication scheme match the service's current contract.

The repository also includes examples\petstore\openapi.yaml, a separate OpenAPI 3.0 teaching fixture. Its /v1/pets route does not match the legacy public service's current /v2 API, so use the live spec for the network example below.

Use the public example responsibly. Do not send credentials, customer data, or mutating requests. For other APIs, run only against a target you are authorized to test and that is confirmed non-production.
1

Choose a Swagger/OpenAPI specification

The input spec defines the API contract: operations, parameters, response codes, schemas, and optionally a server URL. Petstore is just the example—use your own local JSON/YAML spec in the same workflow.

Live service contractSwagger Petstore v2 Swagger JSON is downloaded in the next step.
OpenAPI teaching fixtureexamples\petstore\openapi.yaml · OpenAPI 3.0 example

Download a local copy of the live Swagger spec. The parser reads this local file and does not fetch external references.

New-Item -ItemType Directory -Force test-results | Out-Null
curl.exe --fail --location --silent --show-error https://petstore.swagger.io/v2/swagger.json -o test-results\petstore-live-swagger.json

Optional: inspect the derived plan without entering the guided approval flow.

npx.cmd tsx src/cli.ts analyze --spec test-results\petstore-live-swagger.json --out test-results\petstore-live-plan.md

The plan contains stable case IDs, expected results, sample-value provenance, uncertainty notes, and links back to the spec.

2

Generate candidates and review them

Start the guided workflow. It reads and validates the spec, then explains the cases it derived. The objective helps frame your review; it does not override facts in the spec.

npx.cmd tsx src/cli.ts guide --spec test-results\petstore-live-swagger.json --objective "Check a read-only Petstore inventory operation" --out tests\generated\onboarding-petstore.spec.ts --audit test-results\onboarding-workflow.jsonl

Find the read-only inventory candidate with this stable ID:

TC-GETINVENTORY-POS-200 · GET /store/inventory · expected HTTP 200

Review its expected response, required authentication, risk, and Swagger evidence. Other Petstore cases include writes, unsupported/missing samples, or manual-review-only scenarios; they are not part of this smoke test.

Review means more than accepting a generated sample. Samples are derived from examples/defaults/schema and may not identify a real resource. Negative cases remain manual-review until a safe trigger is chosen.
3

Select exactly what to include, then approve

At the case-selection prompt, enter only the inventory ID. Do not enter all for this public-service walkthrough.

TC-GETINVENTORY-POS-200

Check that the CLI reports one selected case. At the approval prompt, type the exact word:

APPROVE

The generated file is tests\generated\onboarding-petstore.spec.ts. The audit log is test-results\onboarding-workflow.jsonl. Approval is tied to this selection and plan revision; changing the selection invalidates it.

Generation sends no requests. You can inspect the generated TypeScript before deciding whether to run it.
4

Automate the approved read-only case

The live Swagger contract declares the sample API key special-key for inventory. Supply it only to this public demo request, and use Node's Windows system certificate store if this machine's trusted TLS issuer is not in Node's default CA bundle. TLS verification stays enabled.

$oldNodeOptions = $env:NODE_OPTIONS
$oldPetstoreKey = $env:API_KEY_API_KEY
try {
  $env:NODE_OPTIONS = "--use-system-ca"
  $env:API_KEY_API_KEY = "special-key"
  $confirmations = "AUTHORIZED NON-PRODUCTION`nAUTHENTICATION CONFIGURED`nRUN APPROVED`n"
  $confirmations | npx.cmd tsx src/cli.ts run --base-url https://petstore.swagger.io/v2 --file tests\generated\onboarding-petstore.spec.ts --results test-results\petstore-onboarding-results.json --audit test-results\petstore-onboarding-run.jsonl
} finally {
  $env:NODE_OPTIONS = $oldNodeOptions
  $env:API_KEY_API_KEY = $oldPetstoreKey
}

The three confirmation lines above automate this tutorial example; when using it interactively, type each phrase yourself only after reviewing the target and approved plan.

  1. At the target prompt, type AUTHORIZED NON-PRODUCTION only for this public demo and read-only request.
  2. At the authentication prompt, type AUTHENTICATION CONFIGURED to confirm the documented sample key is in use.
  3. At the execution prompt, type RUN APPROVED to run the selected plan revision.

The runner checks approval metadata, restricts the run to the generated test file, avoids automatic redirects, and enforces a time limit. It records a redacted JSON result and local audit events.

The Petstore demo may change, rate-limit requests, or be temporarily offline. A failed live assertion is evidence about this run—not proof that the generator is broken. Inspect the recorded status and test diagnostic. Never use the public demo key for another system.
5

Inspect the result and continue safely

After the run, review:

  • test-results\petstore-onboarding-results.json — outcome, stable case ID, expected/actual status where available, and plan/spec/target fingerprints.
  • test-results\onboarding-workflow.jsonl and test-results\petstore-onboarding-run.jsonl — local events for plan review/approval, target confirmation, and execution outcome.
  • The generated test file and console output — compare the API's behavior to the documented expectation.
Verified smoke-test shape: one case, TC-GETINVENTORY-POS-200, issues GET /store/inventory with the spec's demo API key and checks documented HTTP 200 plus the response contract.

Apply the workflow to another spec

Replace the sample spec path in guide, review every candidate and sample against your API, select only the intended cases, and approve. Before run, use a confirmed authorized non-production target and required environment-based credentials. Mutating cases need both the run option and a separate confirmation; keep them out of this Petstore example.

npx.cmd tsx src/cli.ts guide --spec path\to\your-openapi.yaml --objective "Describe the testing goal"

For validation without any network access, use npm.cmd run typecheck, npm.cmd test, and npm.cmd run build. The test suite uses local fixtures/mocks.

What the agent does—and does not do

It does: parse generic Swagger 2.0/OpenAPI 3.x specs, derive explainable candidate tests, preserve evidence/provenance, require explicit plan approval, then separately confirm execution target and intent.

It does not: infer undocumented behavior, guess safe negative inputs, run unapproved low-level generated files, choose an LLM/provider, or make execution safe against someone deliberately editing code. Treat generated tests as proposals that require human review.

See README, project backlog, and agent contract for full behavior and limitations.
